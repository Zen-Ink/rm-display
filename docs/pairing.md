# Server-authoritative QR pairing

Pairing starts with an offer generated by the receiver from its live server
configuration. Managed PSK mode, which is the receiver default, uses version 2:

```text
rm-display://pair/v2?host=192.168.1.42&host=10.11.99.1&port=7420&security=psk&server=0123456789abcdef0123456789abcdef&psk=64-lowercase-hex-digits
```

This is a server-authoritative offer, not a producer-authored connection
profile. A producer either accepts the advertised endpoint, transport mode,
identity, and credential or aborts. It must not silently replace them, retry a
failed PSK connection as plaintext, or reinterpret an IP range as a security
policy.

The fields are:

- `host`: one to four IPv4 literals. For a wildcard bind, the receiver takes a
  non-polling interface snapshot and orders eligible addresses by interface:
  `wlan0`, then `usb0`, then other active interfaces. An explicit bind publishes
  only that address.
- `port`: the receiver's bound TCP port.
- `security`: exactly `plain` or `psk`; this selects the required record layer
  before any Protobuf message is exchanged.
- `server`: the 16-byte `ServerHello.server_id` as 32 lowercase hexadecimal
  digits. The producer pins it for the attempt and rejects another identity.
- `psk`: exactly 32 random bytes encoded as 64 lowercase hexadecimal digits.
  It is required by version 2 when `security=psk` and forbidden for plaintext.

The QR is a bearer credential. It must not be written to logs, analytics,
screenshots, crash reports, or ordinary application preferences. The reference
Android producer keeps the decoded PSK only in app-process memory. Anyone who
can scan or copy an active QR can authenticate until the key is rotated.

The producer connects using exactly the offered transport. Once that transport
is established, `ClientHello`/`ServerHello` verifies the pinned identity and
negotiates protocol versions, encodings, pixel formats, input capabilities,
credits, and display geometry. These protocol capabilities are negotiated; the
server endpoint, security mode, identity, and credential are not.

Transport selection cannot be deferred to an ordinary plaintext Protobuf
message: such a STARTTLS-style selector would itself be unauthenticated and
would introduce a downgrade surface before PSK authentication. Therefore the
server advertises the transport out of band and both sides enter plain TCP or
TLS-PSK immediately after connect.

## Managed-key lifecycle

At first startup the receiver generates one 32-byte PSK from the operating
system CSPRNG and stores it with mode `0600`. It also persists its random
server identity. Both remain unchanged across producer disconnects, reconnects,
and receiver restarts. The default state directory is
`$XDG_STATE_HOME/rm-display`, falling back to
`$HOME/.local/state/rm-display`; if neither variable exists, a `.state`
directory beside the executable is used. No state or temporary replacement
file is placed under `/tmp`.

Selecting `NEW PAIR` in the receiver-owned power-key menu performs one local,
authoritative transition:

1. close the current producer session, if any;
2. generate and atomically persist a replacement PSK;
3. install the replacement TLS server context and invalidate the old credential;
4. display a replacement QR.

The server identity remains unchanged during this transition; it identifies
the receiver installation, while the PSK identifies the current pairing.
`--server-id` can still provide an explicit identity.

The power-key menu works before the first connection and between connections.
The receiver blocks in `poll(2)` on the listener, power eventfd, and touchscreen,
so this idle behavior neither depends on a producer-created Surface nor polls
input state on a timer.

`--plaintext` emits a version-2 offer with `security=plain` and no `psk`. This
mode has no peer authentication or confidentiality. `--psk-file` selects an
operator-provisioned persistent key path; it is useful with `--no-pairing-qr`
for unattended installations. `NEW PAIR` atomically replaces that file.
Suppressing the QR is rejected for a generated key because no producer could
obtain that credential.

Version-1 PSK offers did not carry a credential. The Android producer accepts
them only as a legacy manual-provisioning flow. Current receivers emit version
2 and never downgrade a version-2 PSK offer to that behavior.
